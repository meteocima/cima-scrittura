# Tipi di documento del dominio progetti

Struttura di riferimento quando l'utente non fornisce un template. Il
template del programma, del progetto o del consorzio prevale sempre:
se esiste, seguirlo sezione per sezione, anche nei titoli.

## Deliverable di tipo report (R)

Pagina iniziale e metadati, se il consorzio non ha un template:

| Campo | Valore |
|---|---|
| Deliverable | codice e titolo come nella DoA |
| Work package / task | |
| Lead beneficiary | |
| Type / Dissemination level | come nella DoA |
| Due date (DoA) / Submission date | |
| Versione e storia delle revisioni | |
| Autori e revisori interni | |

Sezioni:

1. **Executive summary**: cosa contiene il deliverable, il risultato
   principale con il suo dato, il collegamento all'obiettivo della
   DoA. Leggibile da solo (max 1 pagina).
2. **Introduction**: scopo del deliverable, task che lo producono,
   rapporto con altri deliverable e WP.
3. **Corpo**: metodi, dati, risultati, nella struttura richiesta dal
   contenuto. Dati e figure con fonte.
4. **Deviations** (se ci sono): cosa differisce dalla DoA, perché,
   conseguenze, azioni.
5. **Conclusions and next steps**: cosa ne fanno i task successivi.
6. **References** e **Annexes**.

## Deliverable non report (DEM, DEC, DATA, OTHER)

Il deliverable è il prodotto (software, dataset, sito, dimostratore);
il testo è una nota di accompagnamento breve: cosa è, dove si trova
(link, DOI, repository), licenza e accesso, come si verifica che
funziona, collegamento alla DoA. Non gonfiarla in un report.

## Data Management Plan (DMP)

Seguire il template indicato dal programma (per Horizon Europe:
template del Portal, principi FAIR). Ogni dataset ha la sua riga:
nome, origine, formato, volume, repository, licenza, accesso,
metadati, conservazione, responsabile. Dati mancanti: segnaposto.

## Periodic report, parte tecnica

Seguire la Part B del programma (vedi `programmi/<programma>.md`).
Regole comuni:

- per WP: obiettivi del periodo, lavoro svolto per task con il
  contributo dei partner, risultati con prova, deliverable e milestone
  del periodo con stato;
- impatto: avanzamento verso i KPI con valore misurato e baseline;
- scostamenti: sezione dedicata, uno per voce, con causa, effetto,
  azione correttiva e nuova data;
- follow-up delle raccomandazioni precedenti, se il template lo
  prevede, in tabella.
Non ripetere ciò che la Part A (o il sistema del programma) contiene
già: rinviarvi.

## Technical report

Report tecnico non vincolato a un template di programma (per
committenti, agenzie, partner istituzionali). Struttura: summary,
contesto e obiettivo, dati e metodi, risultati, limiti e incertezze,
raccomandazioni o prossimi passi, riferimenti. Il registro è tecnico;
le regole di tracciabilità valgono se il report riferisce attività di
un progetto.

## Executive summary e publishable summary

- Executive summary: 1 pagina; problema, cosa è stato fatto, risultato
  principale con il dato, cosa cambia per chi legge, prossimi passi.
- Publishable summary (Horizon Europe, Part A): max 7.480 caratteri,
  per un pubblico non specialistico, senza dati riservati; contesto e
  obiettivi, lavoro svolto e risultati, risultati attesi e impatto.
- Highlights (Interreg): max 5.000 caratteri, comprensibili da non
  specialisti.

Contare i caratteri prima della consegna quando c'è un limite.
